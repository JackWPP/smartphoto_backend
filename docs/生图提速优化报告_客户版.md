# 生图提速优化报告（客户版）

## 1. 结论
当前 SmartPhoto 生图链路已经完成一轮“机制性提速”改造，重点不是单点堆机器，而是减少前端阻塞、减少无效重试、提高队列利用率和上游任务并发效率。现阶段我们可以明确说明已经完成的优化机制，但不对外虚报统一 benchmark 数字。

## 2. 已完成的提速动作

### 2.1 全链路 job 化
- 主图和详情页正式生成都已走异步 job。
- 前端不再等待整轮生图在单个 HTTP 请求里同步完成。
- 配合 Job Monitor 和事件流，用户可以看到排队、执行、完成过程。

### 2.2 主图与详情页双队列拆分
- 主图走 `q.generation.main`
- 详情页走 `q.generation.detail`
- 两类任务互不阻塞，便于单独扩容和调参。

### 2.3 批量提交上游任务，集中轮询
- 不再按“单张图提交完再等结果”的串行模式执行。
- 当前链路会先批量提交全部上游任务，再集中轮询结果。
- 这样能显著减少等待窗口里的空转时间。

### 2.4 并发下载图片落盘
- 上游返回结果后，图片下载和落盘采用并发处理。
- 减少整组结果在最后一公里串行写盘的时间损耗。

### 2.5 主图与详情页独立并发度配置
- 主图、详情页、上游提交并发都可以分别配置。
- 可以根据上游模型、服务器带宽和 Redis/Worker 压力做更细粒度调优。

### 2.6 白底分支局部重试
- 白底图失败不再直接拖整组任务重跑。
- 当前白底校验会优先做局部重试，降低重复额度消耗和整体耗时。

### 2.7 优先走参考图编辑接口
- 对参考图驱动强的场景，优先走编辑链路而不是完全从零生成。
- 这样通常能减少多轮人工试错与回滚。

### 2.8 历史版本与 prompt 快照持久化
- 每一轮结果都会保存版本和 prompt 快照。
- 运营或设计复盘时不需要重新猜参数，能减少二次试错成本。

## 3. 当前可调性能参数

### `main_generation_concurrency`
- 主图生成内部并发度。
- 值越高，单次主图整组执行更快，但对上游和本机资源压力更大。

### `detail_generation_concurrency`
- 详情页 panel 生成内部并发度。
- 建议和主图分开调，不同任务体量差异较大。

### `generation_submit_concurrency`
- 批量提交上游任务时的提交并发度。
- 主要影响“把任务送上游”这一段的启动速度。

### `WHATAI_REQUEST_TIMEOUT_SECONDS`
- 单次 WhatAI 请求超时。
- `JSON` 请求和 `/v1/images/edits` 的 multipart 请求共用这个值。
- 默认值已收紧到 `90s`，如果长尾请求更明显，可以再适度放宽。

### `image_poll_profile`
- 上游任务结果轮询策略。
- 决定每轮轮询间隔和总轮询窗口。

### `image_task_timeout_seconds`
- 单个上游图片任务的最长等待窗口。
- 过短会导致已成功但稍晚返回链接的任务被误判失败。

## 4. 下一步建议观测指标
- 各 `job_type` 平均耗时
- 队列等待时间
- 上游成功率 / 失败率
- 白底分支命中率
- 单图级局部重试率
- 不同平台规则包下的平均生成时间

## 5. 当前对外口径建议
- 可以明确说：我们已经完成了异步化、队列拆分、批量提交、并发下载、局部重试和版本沉淀等机制性优化。
- 不建议直接承诺“固定提速百分比”，因为最终耗时还会受上游模型、网络出口、参考图复杂度和当时队列压力影响。
- 更稳妥的口径是：系统已经具备可持续调优的结构，而不是只能靠人工盯单点瓶颈。
