# SmartPhoto 原生部署指南

这份文档只回答一件事：如何把 SmartPhoto Backend 部署成当前推荐的生产形态。

默认生产形态固定为：

- `Postgres` 由 `docker-compose.infra.yml` 托管
- `Redis` 由 `docker-compose.infra.yml` 托管
- `API` 由宿主机 `systemd + Python .venv` 托管
- `Worker` 由宿主机 `systemd + Python .venv` 托管
- `Alembic` 由宿主机 `systemd + Python .venv` 托管
- 业务配置统一读取 `shared/.env.prod.native`

一句话就是：

**Docker 只跑基础设施，业务服务原生运行。**

## 1. 目标目录结构

推荐固定目录：

```bash
/opt/smartphoto_backend/
  repo/                        # Git 工作目录
  shared/
    .env.prod.native           # 原生 API/Worker/Migrate 真正读取的生产 env
    storage/                   # 本地 storage 与 admin.sqlite3
  backups/                     # 备份目录
  logs/                        # 可选自定义日志目录
```

说明：

- 文档统一以 `/opt/smartphoto_backend` 为推荐路径。
- 脚本会按当前仓库根目录工作，不强依赖你必须叫这个名字。
- 如果你已经把仓库放在别的目录，后续命令里的路径按实际替换，不要混着用 `/www/wwwroot/...` 和 `/opt/...`。

## 2. 原生部署的固定约束

- 原生服务必须读取 `shared/.env.prod.native`。
- 原生服务连接数据库与 Redis 时必须使用 `127.0.0.1`，不要写 `postgres` 或 `redis`。
- `STORAGE_ROOT` 必须是绝对路径，不能再用 `./storage`。
- `ADMIN_DATABASE_URL` 必须指向 shared storage 下的绝对 sqlite 路径。
- Docker 全应用部署不是默认形态，只保留给历史兼容或紧急回滚。

最小正确示例：

```env
DATABASE_URL=postgresql+psycopg://smartphoto:<password>@127.0.0.1:5432/smartphoto
REDIS_URL=redis://127.0.0.1:6379/0
STORAGE_ROOT=/opt/smartphoto_backend/shared/storage
ADMIN_DATABASE_URL=sqlite:////opt/smartphoto_backend/shared/storage/admin.sqlite3
```

## 3. 首次切换前备份

切到原生前至少备份三样东西：

- PostgreSQL 数据库
- 旧应用容器内的 `/app/storage`
- 服务器现有 `.env.prod`

```bash
set -euo pipefail

export COMPOSE_PROJECT_NAME=smartphoto_backend
export APP_ROOT=/opt/smartphoto_backend
export REPO_ROOT=/opt/smartphoto_backend/repo
export BACKUP_DIR=/opt/smartphoto_backend/backups/native_$(date +%Y%m%d_%H%M%S)

mkdir -p "$BACKUP_DIR"
cd "$REPO_ROOT"

set -a
source .env.prod
set +a

docker compose --env-file .env.prod -f docker-compose.infra.yml up -d postgres redis

docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" smartphoto_backend-postgres-1 \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc \
  > "$BACKUP_DIR/${POSTGRES_DB}_$(date +%Y%m%d_%H%M%S).dump"

docker cp smartphoto_backend-api-1:/app/storage/. "$BACKUP_DIR/storage_from_api_container" || true
cp .env.prod "$BACKUP_DIR/.env.prod.backup"

ls -lh "$BACKUP_DIR"
```

如果你的旧环境还在跑全 Docker，但 `api` 容器名不同，先用 `docker ps --format '{{.Names}}'` 查真实容器名再替换。

## 4. 准备基础设施容器

生产推荐只拉起基础设施：

```bash
set -euo pipefail

cd /opt/smartphoto_backend/repo
export COMPOSE_PROJECT_NAME=smartphoto_backend

docker compose --env-file .env.prod -f docker-compose.infra.yml up -d postgres redis
docker compose --env-file .env.prod -f docker-compose.infra.yml ps
```

如果宿主机 `5432` 或 `6379` 已被占用，在 `.env.prod` 增加：

```env
POSTGRES_HOST_PORT=15432
REDIS_HOST_PORT=16379
```

然后原生 env 也要改成对应端口：

```env
DATABASE_URL=postgresql+psycopg://smartphoto:<password>@127.0.0.1:15432/smartphoto
REDIS_URL=redis://127.0.0.1:16379/0
```

## 5. 准备 shared 目录与原生 env

```bash
set -euo pipefail

mkdir -p /opt/smartphoto_backend/shared/storage
mkdir -p /opt/smartphoto_backend/logs

cd /opt/smartphoto_backend/repo
cp .env.prod.native.example /opt/smartphoto_backend/shared/.env.prod.native
```

然后编辑：

```bash
nano /opt/smartphoto_backend/shared/.env.prod.native
```

至少确认这些配置：

```env
APP_ENV=prod
PUBLIC_BASE_URL=https://your-domain.example
CORS_ALLOW_ORIGINS=https://your-frontend.example

DATABASE_URL=postgresql+psycopg://smartphoto:<password>@127.0.0.1:5432/smartphoto
REDIS_URL=redis://127.0.0.1:6379/0

STORAGE_ROOT=/opt/smartphoto_backend/shared/storage
ADMIN_DATABASE_URL=sqlite:////opt/smartphoto_backend/shared/storage/admin.sqlite3
STORAGE_BACKEND=s3
```

还要从旧 `.env.prod` 同步这些真实生产配置：

- `WHATAI_*`
- `LLM_*`
- `OPENROUTER_*`
- `S3_*`
- `IMAGE_SAAS_APP_KEYS`
- `IMAGE_SAAS_DEFAULT_APP_ID`
- `ADMIN_JWT_SECRET`
- `ADMIN_BOOTSTRAP_USERNAME`
- `ADMIN_BOOTSTRAP_PASSWORD`

不要把这些值遗漏在 `.env.prod` 里却忘了同步到 `.env.prod.native`。

## 6. 拷贝旧 storage

如果之前已经在线上跑过，shared storage 要先补齐。

```bash
set -euo pipefail

docker cp smartphoto_backend-api-1:/app/storage/. /opt/smartphoto_backend/shared/storage/ || true
chown -R smartphoto:smartphoto /opt/smartphoto_backend/shared /opt/smartphoto_backend/logs || true

ls -lah /opt/smartphoto_backend/shared/storage | sed -n '1,80p'
```

重点检查：

- `admin.sqlite3` 是否存在
- 本地存储模式下的上传图/生成图是否已经同步出来

## 7. 安装代码依赖

```bash
set -euo pipefail

cd /opt/smartphoto_backend/repo

python3.12 -m venv .venv
./.venv/bin/pip install --upgrade pip setuptools wheel
./.venv/bin/pip install .
```

构建后台前端：

```bash
cd /opt/smartphoto_backend/repo/adminfront
npm ci
npm run build
cd ..
```

如果你明确没有部署后台前端，也可以后续用：

```bash
./scripts/native-deploy.sh --skip-adminfront-build
```

## 8. 安装 systemd 服务

仓库里的模板文件：

- `deploy/systemd/smartphoto-api.service`
- `deploy/systemd/smartphoto-worker.service`
- `deploy/systemd/smartphoto-migrate.service`

安装命令：

```bash
cd /opt/smartphoto_backend/repo
sudo ./scripts/native-install-systemd.sh
```

默认服务用户是 `smartphoto:smartphoto`。如需自定义：

```bash
sudo SERVICE_USER=www SERVICE_GROUP=www-data ./scripts/native-install-systemd.sh
```

安装后检查：

```bash
systemctl daemon-reload
systemctl list-unit-files 'smartphoto-*.service' --no-pager
```

## 9. 首次预检、迁移和启动

先跑原生预检：

```bash
cd /opt/smartphoto_backend/repo
./scripts/native-preflight.sh
```

预检通过后再迁移：

```bash
sudo systemctl start smartphoto-migrate
sudo systemctl status smartphoto-migrate --no-pager -l
```

再启动服务：

```bash
sudo systemctl enable --now smartphoto-api smartphoto-worker
sudo systemctl status smartphoto-api smartphoto-worker --no-pager -l
```

看日志：

```bash
journalctl -u smartphoto-api -n 150 --no-pager
journalctl -u smartphoto-worker -n 200 --no-pager
```

## 10. 首次冒烟

```bash
curl -i http://127.0.0.1:8000/healthz
curl -i http://127.0.0.1:8000/api/admin/v1/auth/health

curl -i -X OPTIONS http://127.0.0.1:8000/api/v2/sessions \
  -H 'Origin: https://your-frontend.example' \
  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: content-type,x-app-key'
```

再做一次总预检：

```bash
cd /opt/smartphoto_backend/repo
./scripts/native-preflight.sh
```

## 11. 后续发版

默认发版命令：

```bash
cd /opt/smartphoto_backend/repo
SYSTEMCTL="sudo systemctl" ./scripts/native-deploy.sh --branch <deploy-branch>
```

无迁移时才允许：

```bash
cd /opt/smartphoto_backend/repo
SYSTEMCTL="sudo systemctl" ./scripts/native-deploy.sh --branch <deploy-branch> --skip-migrate
```

强约束：

- 只要代码里有新的 Alembic revision，就不能加 `--skip-migrate`
- 只要线上已经出现 `UndefinedTable`、`UndefinedColumn`、`relation does not exist`，就不能继续跳过迁移
- 不要用 root 执行 git 同步，建议用部署用户执行脚本，只把 `systemctl` 提权

## 12. 回滚原则

原生部署默认是“代码回滚”，不是“数据回滚”。

纯应用层问题可回滚代码：

```bash
cd /opt/smartphoto_backend/repo
git fetch --all --prune
git reset --hard <known-good-commit-or-tag>

./.venv/bin/pip install .
(cd adminfront && npm ci && npm run build)

sudo systemctl restart smartphoto-api smartphoto-worker
sudo systemctl status smartphoto-api smartphoto-worker --no-pager -l
```

如果这次已经执行过不向后兼容的 migration，不要直接把代码回退当成完整回滚方案。数据回滚要基于前面的 `pg_dump` 备份单独处理。

## 13. 常见问题

### 13.1 API 起不来且日志里还在找 `postgres`

说明原生 env 仍在写 Docker 内网地址。

```bash
grep '^DATABASE_URL=' /opt/smartphoto_backend/shared/.env.prod.native
```

改成 `127.0.0.1` 后重启：

```bash
sudo systemctl restart smartphoto-api smartphoto-worker
```

### 13.2 Worker 不消费任务且日志里还在找 `redis`

```bash
grep '^REDIS_URL=' /opt/smartphoto_backend/shared/.env.prod.native
redis-cli -h 127.0.0.1 -p 6379 ping

sudo systemctl restart smartphoto-worker
```

### 13.3 改了 env 但服务没生效

原生服务不会自动重读 env：

```bash
sudo systemctl restart smartphoto-api smartphoto-worker
```

如果改的是 unit 文件：

```bash
sudo systemctl daemon-reload
sudo systemctl restart smartphoto-api smartphoto-worker
```

### 13.4 `admin.sqlite3` 无法打开

检查：

```bash
ls -lh /opt/smartphoto_backend/shared/storage/admin.sqlite3
grep '^ADMIN_DATABASE_URL=' /opt/smartphoto_backend/shared/.env.prod.native
```

确保 shared storage 存在且权限正确：

```bash
sudo chown -R smartphoto:smartphoto /opt/smartphoto_backend/shared
```

## 14. 最小心智模型

记住这 8 条就够了：

- Docker 只管 `postgres` 和 `redis`
- 原生服务只看 `shared/.env.prod.native`
- 原生服务连 DB/Redis 一律走 `127.0.0.1`
- `STORAGE_ROOT` 和 `ADMIN_DATABASE_URL` 一律用 shared 绝对路径
- 首次或发版前先跑 `./scripts/native-preflight.sh`
- 迁移用 `smartphoto-migrate`
- 发版用 `./scripts/native-deploy.sh`
- 日志统一用 `journalctl -u smartphoto-api` 和 `journalctl -u smartphoto-worker`
