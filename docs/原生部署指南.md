# SmartPhoto 原生部署指南

这份文档讲的是当前推荐的“半原生部署”：

- 数据库 `Postgres` 继续放在 Docker 容器里
- 队列 `Redis` 继续放在 Docker 容器里
- 后端 `API` 原生跑在服务器上，由 `systemd` 守护
- `Worker` 原生跑在服务器上，由 `systemd` 守护
- 数据库迁移 `Alembic` 也在服务器原生 Python 环境里跑
- 代码更新用 `git`，不再每次构建 Docker 镜像

说人话就是：**Docker 只负责两个“基础设施盒子”，真正经常更新的业务代码直接跑在宿主机上。**

这样做的好处是：

- 发布快：不用每次 `docker build`
- 排障直观：看 `journalctl` 就能看到 API/Worker 日志
- 迁移清楚：`alembic upgrade head` 直接连生产库执行
- 数据安全：继续复用原来的 Docker volume，不搬 Postgres 数据

## 1. 先理解新结构

最终目录长这样：

```bash
/opt/smartphoto_backend/
  repo/                         # git 代码目录
  shared/
    .env.prod.native             # 原生 API/Worker/Alembic 用的生产配置
    storage/                     # 本地 storage / admin.sqlite3
  logs/                          # 可选日志目录，主要日志还是看 journalctl
  backups/                       # 备份目录
```

运行方式长这样：

```text
Nginx/CDN/浏览器
        |
        v
宿主机 systemd: smartphoto-api.service
        |
        +--> 127.0.0.1:5432 -> Docker postgres 容器 -> 原 postgres_data volume
        |
        +--> 127.0.0.1:6379 -> Docker redis 容器 -> 原 redis_data volume
        |
        +--> /opt/smartphoto_backend/shared/storage

宿主机 systemd: smartphoto-worker.service
        |
        +--> 同一套 Postgres / Redis / storage
```

最关键的一点：

**原生进程不能再用 `postgres:5432` 和 `redis:6379` 这种 Docker 内网地址。**

原生进程要用：

```env
DATABASE_URL=postgresql+psycopg://smartphoto:<password>@127.0.0.1:5432/smartphoto
REDIS_URL=redis://127.0.0.1:6379/0
```

## 2. 切换前先别急，先备份

切换部署方式前，先备份三样东西：

- PostgreSQL 数据库
- 旧容器里的 `/app/storage`
- 旧 `.env.prod`

在服务器执行：

```bash
set -euo pipefail

export COMPOSE_PROJECT_NAME=smartphoto_backend
export OLD_ROOT=/opt/smartphoto_backend
export BACKUP_DIR=/opt/smartphoto_backend/backups/native_$(date +%Y%m%d_%H%M%S)

mkdir -p "$BACKUP_DIR"
cd "$OLD_ROOT"

set -a
source .env.prod
set +a

docker compose --env-file .env.prod -f docker-compose.prod.yml up -d postgres redis

docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" smartphoto_backend-postgres-1 \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc \
  > "$BACKUP_DIR/${POSTGRES_DB}_$(date +%Y%m%d_%H%M%S).dump"

docker cp smartphoto_backend-api-1:/app/storage "$BACKUP_DIR/storage_from_api_container" || true
cp .env.prod "$BACKUP_DIR/.env.prod.backup"

ls -lh "$BACKUP_DIR"
```

看到 `.dump` 文件和 `.env.prod.backup` 就可以继续。

## 3. 准备代码目录

如果服务器上还没有 `/opt/smartphoto_backend/repo`，先建目录并把代码拉下来。

示例：

```bash
set -euo pipefail

mkdir -p /opt/smartphoto_backend
cd /opt/smartphoto_backend

git clone <your-repo-url> repo
cd repo
git checkout <deploy-branch>
```

如果已经有了：

```bash
cd /opt/smartphoto_backend/repo
git fetch --all --prune
git reset --hard origin/<deploy-branch>
```

注意：

- 不建议用 `root` 用户维护 git 工作区
- 推荐创建一个 `smartphoto` 用户来跑服务和发布
- 如果已经用当前用户部署，也至少保证 systemd unit 里的 `User/Group` 和目录权限一致

## 4. 只启动 Postgres 和 Redis 容器

把旧 `.env.prod` 复制到 repo 目录，给 compose 读取数据库账号密码：

```bash
set -euo pipefail

export COMPOSE_PROJECT_NAME=smartphoto_backend
export OLD_ROOT=/opt/smartphoto_backend
export REPO_ROOT=/opt/smartphoto_backend/repo

cp "$OLD_ROOT/.env.prod" "$REPO_ROOT/.env.prod"
cd "$REPO_ROOT"

docker compose --env-file .env.prod -f docker-compose.prod.yml stop api worker || true
docker compose --env-file .env.prod -f docker-compose.infra.yml up -d postgres redis
docker compose --env-file .env.prod -f docker-compose.infra.yml ps
```

这里发生了什么：

- `api/worker` 容器停掉
- `postgres/redis` 继续跑
- 新的 `docker-compose.infra.yml` 只管理 `postgres/redis`
- 数据卷还是原来的 `smartphoto_backend_postgres_data` 和 `smartphoto_backend_redis_data`
- Postgres 只暴露到宿主机 `127.0.0.1:5432`
- Redis 只暴露到宿主机 `127.0.0.1:6379`

检查一下：

```bash
set -a
source .env.prod
set +a

pg_isready -h 127.0.0.1 -p 5432 -U "$POSTGRES_USER" -d "$POSTGRES_DB"
redis-cli -h 127.0.0.1 -p 6379 ping
```

如果宿主机已经有 5432 或 6379 被占用，就不要硬抢端口。

在 `.env.prod` 里加：

```env
POSTGRES_HOST_PORT=15432
REDIS_HOST_PORT=16379
```

然后重启 infra：

```bash
docker compose --env-file .env.prod -f docker-compose.infra.yml up -d postgres redis
```

后面的 `.env.prod.native` 也要同步改成：

```env
DATABASE_URL=postgresql+psycopg://smartphoto:<password>@127.0.0.1:15432/smartphoto
REDIS_URL=redis://127.0.0.1:16379/0
```

## 5. 准备原生配置

创建共享目录：

```bash
set -euo pipefail

mkdir -p /opt/smartphoto_backend/shared/storage
mkdir -p /opt/smartphoto_backend/logs

cd /opt/smartphoto_backend/repo
cp .env.prod.native.example /opt/smartphoto_backend/shared/.env.prod.native
```

现在编辑：

```bash
nano /opt/smartphoto_backend/shared/.env.prod.native
```

至少确认这几行：

```env
DATABASE_URL=postgresql+psycopg://smartphoto:<真实密码>@127.0.0.1:5432/smartphoto
REDIS_URL=redis://127.0.0.1:6379/0
STORAGE_ROOT=/opt/smartphoto_backend/shared/storage
ADMIN_DATABASE_URL=sqlite:////opt/smartphoto_backend/shared/storage/admin.sqlite3
TASKS_EAGER=false
STORAGE_BACKEND=s3
```

还要把旧 `.env.prod` 里这些生产配置搬过来：

- `PUBLIC_BASE_URL`
- `CORS_ALLOW_ORIGINS`
- `IMAGE_SAAS_APP_KEYS`
- `IMAGE_SAAS_DEFAULT_APP_ID`
- `ADMIN_JWT_SECRET`
- `ADMIN_BOOTSTRAP_USERNAME`
- `ADMIN_BOOTSTRAP_PASSWORD`
- `WHATAI_*`
- `LLM_*`
- `OPENROUTER_*`
- `S3_*`
- 生图并发和轮询相关配置

一个简单但笨稳的办法：

```bash
diff -u /opt/smartphoto_backend/.env.prod /opt/smartphoto_backend/shared/.env.prod.native | less
```

你要做的不是让两份文件完全一样，而是确认：

- 业务密钥一致
- 模型配置一致
- S3 配置一致
- `DATABASE_URL/REDIS_URL/STORAGE_ROOT/ADMIN_DATABASE_URL` 换成原生部署写法

## 6. 拷贝旧 storage

如果生产已经用 S3 保存图片，storage 里最重要的通常是 `admin.sqlite3` 等本地状态。

如果之前是 local storage，storage 里可能还有上传和生成图片，更要认真拷贝。

执行：

```bash
set -euo pipefail

docker cp smartphoto_backend-api-1:/app/storage/. /opt/smartphoto_backend/shared/storage/ || true

chown -R smartphoto:smartphoto /opt/smartphoto_backend/shared /opt/smartphoto_backend/logs || true
ls -lah /opt/smartphoto_backend/shared/storage | sed -n '1,80p'
```

如果服务器上没有 `smartphoto` 用户，把 `chown` 换成实际运行服务的用户。

## 7. 安装 Python 和前端依赖

在 repo 目录执行：

```bash
set -euo pipefail

cd /opt/smartphoto_backend/repo

python3.12 -m venv .venv
./.venv/bin/pip install --upgrade pip setuptools wheel
./.venv/bin/pip install .
```

构建后台管理台：

```bash
cd /opt/smartphoto_backend/repo/adminfront
npm install
npm run build
cd ..
```

如果服务器没有 Python 3.12 或 Node 20，先安装系统依赖。

Ubuntu/Debian 示例：

```bash
sudo apt-get update
sudo apt-get install -y python3.12 python3.12-venv postgresql-client redis-tools curl git
```

Node 建议用服务器现有 Node 20 安装方式；如果没有，请按你们服务器标准方式安装，不建议在生产机随手混多个 Node 版本。

## 8. 安装 systemd 服务

仓库里已经有模板：

```bash
deploy/systemd/smartphoto-api.service
deploy/systemd/smartphoto-worker.service
deploy/systemd/smartphoto-migrate.service
```

默认服务用户是：

```ini
User=smartphoto
Group=smartphoto
```

如果你不是用 `smartphoto` 用户跑服务，先改这三份 unit。

安装：

```bash
cd /opt/smartphoto_backend/repo
sudo ./scripts/native-install-systemd.sh
```

它会把 unit 复制到 `/etc/systemd/system/`，然后执行：

```bash
systemctl daemon-reload
systemctl enable smartphoto-api.service smartphoto-worker.service
```

## 9. 先跑迁移，再启动服务

迁移：

```bash
sudo systemctl start smartphoto-migrate
sudo systemctl status smartphoto-migrate --no-pager
```

如果失败，先看日志，不要继续启动 API/Worker：

```bash
journalctl -u smartphoto-migrate -n 200 --no-pager
```

迁移成功后启动：

```bash
sudo systemctl enable --now smartphoto-api smartphoto-worker
sudo systemctl status smartphoto-api smartphoto-worker --no-pager
```

看日志：

```bash
journalctl -u smartphoto-api -n 150 --no-pager
journalctl -u smartphoto-worker -n 200 --no-pager
```

## 11. 以后怎么发版

以后正常发布就不需要重新搞上面的全部流程。

常规发布：

```bash
cd /opt/smartphoto_backend/repo
SYSTEMCTL="sudo systemctl" ./scripts/native-deploy.sh --branch <deploy-branch>
```

这个脚本会做：

1. `git fetch --all --prune`
2. `git reset --hard origin/<deploy-branch>`
3. 安装 Python 包
4. 构建 `adminfront`
5. 停 API/Worker
6. 跑 `smartphoto-migrate`
7. 启 API/Worker
8. 打印 systemd 状态

如果你非常确定这次没有数据库迁移：

```bash
cd /opt/smartphoto_backend/repo
SYSTEMCTL="sudo systemctl" ./scripts/native-deploy.sh --branch <deploy-branch> --skip-migrate
```

但这里要记住一句话：

**只要代码里有新的 Alembic revision，就不要 `--skip-migrate`。**

如果线上已经报：

- `UndefinedTable`
- `UndefinedColumn`
- `relation ... does not exist`

那也不要继续跳过迁移，直接补跑：

```bash
sudo systemctl start smartphoto-migrate
sudo systemctl status smartphoto-migrate --no-pager
sudo systemctl restart smartphoto-api smartphoto-worker
```

## 12. 回滚怎么做

如果只是应用代码问题，并且这次没有不可逆数据库迁移，可以回滚 git 代码：

```bash
cd /opt/smartphoto_backend/repo
git fetch --all --prune
git reset --hard <known-good-commit-or-tag>

./.venv/bin/pip install .
(cd adminfront && npm install && npm run build)

sudo systemctl restart smartphoto-api smartphoto-worker
sudo systemctl status smartphoto-api smartphoto-worker --no-pager
```

如果这次已经执行了数据库迁移，回滚前先判断迁移是否向后兼容。

说人话就是：

- 只改 Python 逻辑：通常可以回滚代码
- 加了字段但旧代码不用：通常还能回滚代码
- 删字段、改字段语义、重写数据：不能把“回滚代码”当成“回滚数据”
- 真要回滚数据，用第 2 步备份出来的 `pg_dump`，并接受停机窗口

## 13. 常见问题

### API 启动后连不上数据库

先看原生 env：

```bash
grep '^DATABASE_URL=' /opt/smartphoto_backend/shared/.env.prod.native
```

如果里面还是：

```text
@postgres:5432
```

那就是 Docker 内网地址，原生进程用不了。

改成：

```text
@127.0.0.1:5432
```

然后：

```bash
sudo systemctl restart smartphoto-api smartphoto-worker
```

### Worker 一直不消费任务

看 Redis 地址：

```bash
grep '^REDIS_URL=' /opt/smartphoto_backend/shared/.env.prod.native
redis-cli -h 127.0.0.1 -p 6379 ping
journalctl -u smartphoto-worker -n 200 --no-pager
```

如果还是 `redis://redis:6379/0`，改成：

```env
REDIS_URL=redis://127.0.0.1:6379/0
```

### 端口 5432 或 6379 被占用

在 repo 的 `.env.prod` 里加：

```env
POSTGRES_HOST_PORT=15432
REDIS_HOST_PORT=16379
```

重启 infra：

```bash
cd /opt/smartphoto_backend/repo
docker compose --env-file .env.prod -f docker-compose.infra.yml up -d postgres redis
```

然后改 `/opt/smartphoto_backend/shared/.env.prod.native`：

```env
DATABASE_URL=postgresql+psycopg://smartphoto:<password>@127.0.0.1:15432/smartphoto
REDIS_URL=redis://127.0.0.1:16379/0
```

最后：

```bash
sudo systemctl restart smartphoto-api smartphoto-worker
```

### 迁移失败

看日志：

```bash
journalctl -u smartphoto-migrate -n 200 --no-pager
```

常见原因：

- `DATABASE_URL` 写错
- 数据库容器没启动
- 密码不对
- 当前 schema 和代码 migration 链不一致

先不要启动新 API/Worker，避免新代码连旧 schema 报错。

### 后台登录状态或 admin 用户不对

先确认 `admin.sqlite3` 是否在共享 storage 里：

```bash
ls -lh /opt/smartphoto_backend/shared/storage/admin.sqlite3
grep '^ADMIN_DATABASE_URL=' /opt/smartphoto_backend/shared/.env.prod.native
```

如果旧文件没拷过来，从容器再拷一次：

```bash
docker cp smartphoto_backend-api-1:/app/storage/admin.sqlite3 /opt/smartphoto_backend/shared/storage/admin.sqlite3
chown smartphoto:smartphoto /opt/smartphoto_backend/shared/storage/admin.sqlite3
sudo systemctl restart smartphoto-api
```

### 改了 env 但不生效

systemd 服务不会自动重读 env 文件。

改完 `/opt/smartphoto_backend/shared/.env.prod.native` 后执行：

```bash
sudo systemctl restart smartphoto-api smartphoto-worker
```

如果改了 unit 文件本身，再执行：

```bash
sudo systemctl daemon-reload
sudo systemctl restart smartphoto-api smartphoto-worker
```

## 14. 最小心智模型

记住这几条就够了：

- Docker 现在只管 `postgres` 和 `redis`
- API/Worker 是宿主机 systemd 服务
- 原生配置文件是 `/opt/smartphoto_backend/shared/.env.prod.native`
- 原生进程连 DB/Redis 用 `127.0.0.1`
- 代码发布用 `scripts/native-deploy.sh`
- 数据库迁移用 `smartphoto-migrate`
- 只要有新 migration，就不要跳过迁移
- 看 API 日志：`journalctl -u smartphoto-api`
- 看 Worker 日志：`journalctl -u smartphoto-worker`
