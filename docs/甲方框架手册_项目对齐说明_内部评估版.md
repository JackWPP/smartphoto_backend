# 甲方《SmartPhoto 框架手册》项目对齐说明（内部评估版）

## 1. 手册核心诉求拆解

甲方手册的核心不是再加几个 Prompt 词，而是把当前固定模板式生成，升级为“槽位 + 表达方式菜单 + Prompt 模块化”的策略系统。结合现有项目，核心诉求可以拆成两块：

### 1.1 主图侧诉求

- 仍然保留 5 张位心智，但每个槽位不再绑定唯一模板。
- 每个槽位需要支持多个表达方式候选，并允许 AI 推荐与用户覆盖。
- Prompt 需要从“固定 role 规则”升级为“role + expression_mode 组合规则”。

### 1.2 详情页侧诉求

- 详情页不希望固定成同一套 8 panel 模板。
- 需要有 14 类板块类型库，并由 AI 根据商品类型推荐 8 个组合。
- 用户需要能够在固定数量内切换板块类型、调整顺序，并自动联动 Prompt 变化。

## 2. 已实现的底盘

### 2.1 Session / Jobs / Job Events / Assets 持久化真相已落地

现状：会话状态、任务状态、事件流、结果资产、幂等记录都已落库，前端不依赖进程内内存状态。

依据：当前项目已经具备 `sessions`、`jobs`、`job_events`、`assets`、`idempotency_records` 等核心模型，并通过 API + Worker 闭环运行。

### 2.2 主图固定 5 role 已落地

现状：主图链路当前固定为 `hero`、`white_bg`、`selling_point`、`scene`、`detail` 五类 role，并且生成顺序、展示顺序、单图重生成语义都建立在这套 role 模型上。

依据：当前 `strategy_preview.asset_plan`、Prompt 生成逻辑、主图结果列表和集成测试都明确依赖这 5 个固定 role。

### 2.3 Prompt 结构化 blocks 与 preview 已落地

现状：当前 Prompt 不是单串文本，而是按 `goal`、`subject`、`composition`、`background`、`style`、`selling_points`、`constraints`、`instruction` 结构化组装，并支持只读预览。

依据：已有主图 `prompts/preview`、策略预览、实际执行 `prompt_snapshot` 和 `generation_snapshot` 追溯能力。

### 2.4 详情页固定 8 panel + 1 stitched 已落地

现状：详情页链路当前固定输出 8 张 `21:9` panel 图，再拼成 1 张 stitched 长图；商品图与风格图分离上传，版本号独立维护。

依据：当前 `detail_strategy_preview.panel_plan`、详情页生成 job、结果结构和下载逻辑都围绕固定 8 panel 建立。

### 2.5 幂等、锁、版本追溯、下载闭环已落地

现状：主图和详情页都已具备幂等键复用、并发互斥、版本递增、父子追溯、结果下载等底层机制。

依据：主图生成、整组重生成、单图重生成、详情页生成都有对应 job、事件流和结果接口。

## 3. 能马上加的功能

以下能力都属于“策略层加字段和规则”，低风险前提是保持当前固定 5 主图和固定 8 panel 的执行主干不变。

### 3.1 在 `strategy_preview.asset_plan/prompt_plan` 中增加 `expression_mode`

为什么低风险：当前主图链路已经有 `asset_plan` 和 `prompt_plan` 两层结构，增加 `expression_mode`、`expression_label`、`expression_reason` 这类元数据，属于结构增量，不会破坏现有 job 执行模型。

建议范围：先只支持固定 5 槽位内切换表达方式，不改槽位数量，不改结果数据模型。

### 3.2 在 Step 5 请求体中增加主图槽位表达方式选择参数

为什么低风险：当前 Step 5 已经支持 `planner_instruction`，本质上已经有“按预览参数重建策略”的入口。继续扩一个“每个槽位选什么表达方式”的请求结构，属于自然延伸。

注意点：后续如果落实现，需要同步改 `/api/v2/sessions/{session_id}/strategy/preview`、`/prompts/preview` 以及主图生成入口的请求/响应元数据。

### 3.3 基于 `planner_instruction + analysis_snapshot + confirmed_copy` 做 AI 推荐表达方式

为什么低风险：当前系统已经具备商品分析结果、文案字段、参考图清单和 LLM Planner 能力，可以在现有 Planner 上追加“给每个槽位推荐表达方式”的判断，而不必改任务执行层。

建议方式：先让后端生成推荐值和推荐理由，前端负责展示与覆盖。

### 3.4 在 `detail_strategy_preview.panel_plan` 中增加 `panel_type`

为什么低风险：详情页当前已经有 `panel_plan` 抽象，每个 panel 都有 `panel_id`、`panel_label`、`layout_notes`、`planner_prompt_base` 等字段。追加 `panel_type` 和 `panel_type_reason` 属于同层元数据扩展。

建议范围：先做固定 8 个 panel 槽位内的类型切换，不动固定 8 张产出约束。

### 3.5 允许详情页 8 个固定 panel 在 14 类板块库内换类型和排序，但总数仍保持 8

为什么低风险：这会改变策略规划和 Prompt 规则，但不改变最终仍是 8 张 panel + 1 张 stitched 的执行语义；对存储、事件流、下载和版本模型影响相对可控。

建议方式：保持 `panel_count = 8`、`aspect_ratio = 21:9`、`stitched` 结果不变，仅提升 `panel_plan` 的可配置性。

## 4. 影响稳定性做不了的内容

这里的“做不了”是指当前阶段不建议纳入，因为会直接冲击现有稳定主干，不是理论上完全不可实现。

### 4.1 任意化主图槽位数或顺序

原因：
- 当前主图执行链路基于固定 5 role 建模。
- `white_bg` 有独立白底校验与重试分支，不能简单当成普通 role。
- 结果排序、下载打包、最新版本展示、单图重生成都默认依赖固定 role + display_order。

结论：如果改成任意张位和任意顺序，本质上已经不是“策略增强”，而是主图结果模型重构。

### 4.2 任意化详情页板块数、尺寸规则或长图拼接方式

原因：
- 当前详情页固定 `panel_count = 8`。
- 当前 panel 输出固定 `21:9`，最终再拼出 1 张 stitched 长图。
- 结果接口、下载结构、资产种类和版本语义都已经写死在“8 panel + 1 stitched”假设上。

结论：如果改成任意板块数、任意尺寸、任意拼接规则，会同时动到策略层、执行层、存储层和结果接口。

### 4.3 要求模型稳定输出高准确率图中文字、复杂参数图或品牌故事长文案

原因：
- 当前图像模型对长文本、复杂参数图和排版准确率天然不稳定。
- 一旦业务要求“文字必须准确、可读、几乎零错字”，返工链路会显著拉长。
- 这类诉求更适合拆成图文分层方案，而不是完全寄托于单次 AI 生图。

结论：本期可支持短标题、短卖点、预留文案空间，不建议承诺重文字信息图质量。

## 5. 推荐实施顺序

### P0：先做表达方式层和板块类型层增强

- 主图 `asset_plan/prompt_plan` 增加表达方式元数据。
- Step 5 增加 AI 推荐和用户可选表达方式。
- Prompt 规则从固定 role 扩成 `role + expression_mode`。
- 详情页 `panel_plan` 增加板块类型元数据、推荐理由和固定 8 板块内替换能力。

### P1：再做推荐组合和前端交互增强

- 主图支持“将某表达方式应用到多个槽位”。
- 详情页支持推荐组合回填和面板顺序调整。
- 继续细化推荐理由、预览摘要和 Prompt 调试信息。

### 暂缓：会冲击底盘假设的能力

- 任意主图数量
- 任意详情页板块数
- 任意版式拼接
- 高依赖图中文字正确率的信息图

## 6. 当前文档边界说明

本次只做对齐评估，不改接口、不改实现、不改测试。

但如果后续要落地“能马上加的功能”，需要同步调整 `/api/v2` 中与策略预览、Prompt 预览和生成请求相关的请求/响应结构，否则前后端无法稳定承接这些新增配置项。
