# SmartPhoto 原生运维指南

这份文档只负责日常值班、发版、排障和救火。

默认线上形态固定为：

- `postgres` / `redis` 由 `docker-compose.infra.yml` 托管
- `smartphoto-api.service` 托管 API
- `smartphoto-worker.service` 托管 Worker
- `smartphoto-migrate.service` 托管 Alembic 迁移
- 原生配置统一在 `shared/.env.prod.native`

推荐目录：

- 仓库：`/opt/smartphoto_backend/repo`
- 原生 env：`/opt/smartphoto_backend/shared/.env.prod.native`
- shared storage：`/opt/smartphoto_backend/shared/storage`

一句话记忆：

**Docker 看基础设施，systemd 看业务服务，排障先看原生 env。**

## 1. 每日巡检

```bash
cd /opt/smartphoto_backend/repo

docker compose --env-file .env.prod -f docker-compose.infra.yml ps
systemctl status smartphoto-api smartphoto-worker --no-pager -l
curl -i http://127.0.0.1:8000/healthz
curl -i http://127.0.0.1:8000/api/admin/v1/auth/health
ss -ltnp '( sport = :8000 )'
```

正常预期：

- `postgres` / `redis` 是 `Up`
- `smartphoto-api` / `smartphoto-worker` 是 `active (running)`
- `/healthz` 与 `/api/admin/v1/auth/health` 返回 `200`

## 2. 日志查看

API 问题先看：

```bash
journalctl -u smartphoto-api -n 200 --no-pager -l
```

Worker 问题先看：

```bash
journalctl -u smartphoto-worker -n 200 --no-pager -l
```

迁移问题先看：

```bash
journalctl -u smartphoto-migrate -n 200 --no-pager -l
```

跟随日志：

```bash
journalctl -u smartphoto-api -f
journalctl -u smartphoto-worker -f
```

## 3. 常用运维命令

基础设施：

```bash
cd /opt/smartphoto_backend/repo
export COMPOSE_PROJECT_NAME=smartphoto_backend

docker compose --env-file .env.prod -f docker-compose.infra.yml up -d postgres redis
docker compose --env-file .env.prod -f docker-compose.infra.yml ps
docker compose --env-file .env.prod -f docker-compose.infra.yml logs --tail=100 postgres redis
```

原生服务：

```bash
sudo systemctl restart smartphoto-api smartphoto-worker
sudo systemctl status smartphoto-api smartphoto-worker --no-pager -l
```

原生预检：

```bash
cd /opt/smartphoto_backend/repo
./scripts/native-preflight.sh
```

## 4. 标准发版

默认发版命令：

```bash
cd /opt/smartphoto_backend/repo
SYSTEMCTL="sudo systemctl" ./scripts/native-deploy.sh --branch <deploy-branch>
```

只有明确无 migration 时才允许：

```bash
cd /opt/smartphoto_backend/repo
SYSTEMCTL="sudo systemctl" ./scripts/native-deploy.sh --branch <deploy-branch> --skip-migrate
```

发版前最低要求：

- 先跑 `./scripts/native-preflight.sh`
- 如果本次包含 migration，先做 PostgreSQL 备份
- 不要用 root 执行 git 同步

## 5. 手工跑迁移

迁移服务是 oneshot，跑完后显示 `inactive (dead)` 也可能是正常的。

```bash
sudo systemctl start smartphoto-migrate
sudo systemctl status smartphoto-migrate --no-pager -l
journalctl -u smartphoto-migrate -n 200 --no-pager -l
```

看到 `Finished smartphoto-migrate.service` 通常就是成功。

## 6. 改配置后的正确生效方式

原生配置文件：

```bash
/opt/smartphoto_backend/shared/.env.prod.native
```

改完配置后要显式重启服务：

```bash
sudo systemctl restart smartphoto-api smartphoto-worker
```

如果改的是 systemd unit：

```bash
sudo systemctl daemon-reload
sudo systemctl restart smartphoto-api smartphoto-worker
```

常查配置：

```bash
grep -E '^(DATABASE_URL|REDIS_URL|STORAGE_ROOT|ADMIN_DATABASE_URL|PUBLIC_BASE_URL|CORS_ALLOW_ORIGINS)=' \
  /opt/smartphoto_backend/shared/.env.prod.native
```

必须满足：

- `DATABASE_URL` 指向 `127.0.0.1` 或真实外部 DB 地址
- `REDIS_URL` 指向 `127.0.0.1` 或真实外部 Redis 地址
- `STORAGE_ROOT` 是绝对路径
- `ADMIN_DATABASE_URL` 是 shared storage 下的绝对 sqlite 路径

## 7. Redis 运维

检查 Redis：

```bash
docker compose --env-file .env.prod -f docker-compose.infra.yml exec -T redis redis-cli PING
```

清当前 DB：

```bash
sudo systemctl stop smartphoto-worker
docker compose --env-file .env.prod -f docker-compose.infra.yml exec -T redis redis-cli FLUSHDB
sudo systemctl start smartphoto-worker
```

清所有 DB：

```bash
sudo systemctl stop smartphoto-worker
docker compose --env-file .env.prod -f docker-compose.infra.yml exec -T redis redis-cli FLUSHALL
sudo systemctl start smartphoto-worker
```

除非确认该 Redis 只给 SmartPhoto 用，否则不要轻易 `FLUSHALL`。

## 8. PostgreSQL 备份

任何带 migration 的发布前先备份：

```bash
cd /opt/smartphoto_backend/repo

set -a
source .env.prod
set +a

mkdir -p /opt/smartphoto_backend/backups

docker exec -e PGPASSWORD="$POSTGRES_PASSWORD" smartphoto_backend-postgres-1 \
  pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc \
  > "/opt/smartphoto_backend/backups/${POSTGRES_DB}_$(date +%Y%m%d_%H%M%S).dump"

ls -lh /opt/smartphoto_backend/backups | tail
```

如果还要备份 shared storage：

```bash
tar -czf "/opt/smartphoto_backend/backups/shared_storage_$(date +%Y%m%d_%H%M%S).tar.gz" \
  /opt/smartphoto_backend/shared/storage
```

## 9. 回滚

纯应用层回滚：

```bash
cd /opt/smartphoto_backend/repo
git fetch --all --prune
git reset --hard <known-good-commit-or-tag>

./.venv/bin/pip install .
(cd adminfront && npm ci && npm run build)

sudo systemctl restart smartphoto-api smartphoto-worker
sudo systemctl status smartphoto-api smartphoto-worker --no-pager -l
```

如果本次迁移不向后兼容，不要把代码回滚当成完整回滚。数据库回退必须基于备份单独评估。

## 10. API 起不来怎么救

先停掉重启风暴：

```bash
sudo systemctl stop smartphoto-api
sudo systemctl reset-failed smartphoto-api
```

再看日志：

```bash
journalctl -u smartphoto-api -n 200 --no-pager -l
```

常见判断：

- `failed to resolve host 'postgres'`
  说明原生 env 还在写 Docker 内网地址。
- `sqlite3.OperationalError: unable to open database file`
  说明 shared storage 或 sqlite 路径/权限有问题。

快速核对：

```bash
grep -E '^(DATABASE_URL|STORAGE_ROOT|ADMIN_DATABASE_URL)=' \
  /opt/smartphoto_backend/shared/.env.prod.native

ls -ld /opt/smartphoto_backend/shared /opt/smartphoto_backend/shared/storage
ls -lh /opt/smartphoto_backend/shared/storage/admin.sqlite3
```

修完后：

```bash
sudo systemctl restart smartphoto-api
sudo systemctl status smartphoto-api --no-pager -l
```

## 11. Worker 不跑怎么救

```bash
systemctl status smartphoto-worker --no-pager -l
journalctl -u smartphoto-worker -n 200 --no-pager -l
```

优先检查：

```bash
grep '^REDIS_URL=' /opt/smartphoto_backend/shared/.env.prod.native
docker compose --env-file .env.prod -f docker-compose.infra.yml ps
docker compose --env-file .env.prod -f docker-compose.infra.yml exec -T redis redis-cli PING
```

如果 `REDIS_URL` 里还是 `redis://redis:6379/0`，先改成 `127.0.0.1` 再重启 worker。

## 12. 迁移失败怎么救

```bash
journalctl -u smartphoto-migrate -n 200 --no-pager -l
```

常见原因：

- `DATABASE_URL` 写错
- Postgres 容器没起来
- 密码不对
- 当前代码与数据库 schema 不一致

如果是因为还在连 `postgres`：

```bash
grep '^DATABASE_URL=' /opt/smartphoto_backend/shared/.env.prod.native
```

如果是 `UndefinedTable` / `UndefinedColumn`，说明这次不能再跳过迁移，先修完 schema 再启动 API/Worker。

## 13. 最小救火流程

什么都不确定时，按这个顺序：

```bash
cd /opt/smartphoto_backend/repo

docker compose --env-file .env.prod -f docker-compose.infra.yml ps
systemctl status smartphoto-api smartphoto-worker --no-pager -l
journalctl -u smartphoto-api -n 120 --no-pager -l
journalctl -u smartphoto-worker -n 120 --no-pager -l
grep -E '^(DATABASE_URL|REDIS_URL|STORAGE_ROOT|ADMIN_DATABASE_URL)=' \
  /opt/smartphoto_backend/shared/.env.prod.native
curl -i http://127.0.0.1:8000/healthz
```

判断口径：

- `curl` 不通 8000：先修 API
- API 正常、任务不动：先修 Worker/Redis
- migrate 成功但 API 还崩：多半是 env、shared storage 或 admin sqlite
- 仍在解析 `postgres` / `redis`：原生 env 没改干净

## 15. 真正要记住的 8 条

- 生产默认形态是“Docker 跑 Postgres/Redis，systemd 跑 API/Worker/Migrate”
- 真正生效的原生配置是 `shared/.env.prod.native`
- 原生服务连 DB/Redis 不要写 `postgres` / `redis`
- 发布默认走 `./scripts/native-deploy.sh`
- 发布前默认先跑 `./scripts/native-preflight.sh`
- 带 migration 先备份 PostgreSQL
- 改 env 后必须 `systemctl restart`
- 排障先看 `journalctl`
