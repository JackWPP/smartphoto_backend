# 运行与排障手册

## 1. 开发环境启动

### 1.1 基础命令
```bash
# 1) 启动基础设施
./scripts/dev-up.sh

# 2) 执行迁移（建议首次或显式检查时手动执行）
alembic upgrade head

# 3) 启动 API（会自动补一次 alembic upgrade head）
./scripts/dev-api.sh

# 4) 启动 Worker（会自动补一次 alembic upgrade head）
./scripts/dev-worker.sh
```

无 Docker 本地开发推荐两种模式：

1. 轻量调试模式：`SQLite + TASKS_EAGER=true`
```bash
cp .env.example .env
```

`.env` 至少改成：
```env
DATABASE_URL=sqlite:///./storage/app.sqlite3
ADMIN_DATABASE_URL=sqlite:///./storage/admin.sqlite3
TASKS_EAGER=true
REDIS_URL=redis://localhost:6379/0
STORAGE_BACKEND=local
PUBLIC_BASE_URL=http://127.0.0.1:8000
CORS_ALLOW_ORIGINS=http://127.0.0.1:5173,http://localhost:5173
```

然后只启动：
```bash
./scripts/dev-api.sh
```

2. 接近真实链路模式：`PostgreSQL + Redis + Celery Worker`
```bash
cp .env.example .env
./scripts/dev-api.sh
./scripts/dev-worker.sh
```

说明：

- `TASKS_EAGER=true` 时，不需要 Worker，job 会在 API 进程内直接执行
- `./scripts/dev-api.sh` 会自动执行 `alembic upgrade head`
- `./scripts/dev-api.sh` 默认只监听 `app/ scripts/ alembic/`，不会再扫描 `runtime/`，避免 Docker 残留的 `runtime/postgres` 权限导致 `WatchfilesRustInternalError`
- 若 `8000` 已被占用，`./scripts/dev-api.sh` 会自动顺延到后续空闲端口，并在终端打印实际监听地址
- 如需固定端口，可显式指定：
```bash
PORT=8001 ./scripts/dev-api.sh
```

### 1.2 启动后检查
```bash
# 健康检查
curl -s http://127.0.0.1:8000/healthz

# 后台自检
curl -s http://127.0.0.1:8000/api/admin/v1/auth/health
```

如果 `dev-api.sh` 自动回退到了其他端口，把上面的 `8000` 替换成实际打印端口即可。

预期：`{"code":0,"message":"success","data":{"status":"ok"}}`

### 1.3 后台管理台本地说明
- 后台入口：`http://127.0.0.1:8000/admin`
- 默认建议在 `.env` 中设置：
  - `ADMIN_BOOTSTRAP_USERNAME=admin`
  - `ADMIN_BOOTSTRAP_PASSWORD=admin123456`
- 若历史 `storage/admin.sqlite3` 仍是旧原型结构，当前实现会在检测到缺列时自动补齐 `admin_audit_logs.module/risk_level/operator_note` 等后台控制台新增字段
- 图片 SaaS 鉴权相关环境变量：
  - `IMAGE_SAAS_APP_KEYS`，格式如 `["default:local-dev-app-key"]`
  - `IMAGE_SAAS_DEFAULT_APP_ID`，默认 `default`
- 当前后台前端已升级为路由化控制台，包含：
  - `Overview / Sessions / Jobs / Assets / Prompts / Rule Packs / Audit / System`
- 本地开发建议直接访问 `http://127.0.0.1:8000/admin`，生产静态构建默认由后端 `/admin` 提供
- 重新构建后台前端：
```bash
cd adminfront
npm run build
```

## 2. 生产发布与更新 SOP

以下流程用于单机 Docker Compose 生产环境，项目目录默认：

```bash
cd /opt/smartphoto_backend
```

### 2.1 最小中断原则

- 非必要不执行 `docker compose down`
- 非必要不重启 `postgres`、`redis`
- 绝大多数发布只更新 `api`、`worker`
- 有数据库迁移时，先执行 `migrate`，再重建应用层
- 发布后必须立刻做 `healthz` 和最小业务冒烟

### 2.1.1 仓库内置部署脚本

- `./scripts/package-prod.sh`
  - 生成仅包含 git-tracked 白名单文件、且不含 `.env.prod` 的部署包，输出到 `dist/`
- `./scripts/preflight-prod.sh`
  - 发布前检查 `.env.prod`、容器状态、`alembic_version`、用户表和 `rule_pack*` 实际 schema
- `./scripts/deploy-prod.sh --image-tag <tag>`
  - 本机 `docker build` 新镜像，并仅热更新 `api/worker`
- `./scripts/deploy-prod.sh --image-tag <tag> --skip-migrate`
  - 代码热更新且显式跳过迁移，适合纯逻辑/脚本变更
- `./scripts/rollback-prod.sh <image-ref>`
  - 回滚到已有镜像，不重建 `postgres/redis`

说明：
- 生产机应保留自己的 `.env.prod`，不要把本地 `.env.prod` 打进包里
- `docker-compose.prod.yml` 使用独立 named volume 持久化 `postgres/redis/storage`
- 热更新默认只替换 `api/worker`，数据库卷与 Redis 数据不会被清空
- 包内源码来自 git-tracked 白名单，不会再把本地未跟踪文件打进部署包

### 2.1.2 打部署包

```bash
./scripts/package-prod.sh
```

产物示例：
```bash
dist/smartphoto_backend_deploy_20260322_143000_ab12cd3.tar.gz
```

强烈建议发包前先跑：
```bash
./scripts/preflight-prod.sh
```

### 2.2 推荐：新目录发布（无迁移）

适用场景：
- 仅 Python 代码改动
- 文档、脚本、业务逻辑改动
- 未新增 Alembic migration

```bash
export COMPOSE_PROJECT_NAME=smartphoto_backend
mkdir -p /opt/smartphoto_backend/releases/<release-id>
tar -xzf smartphoto_backend_deploy_<release-id>.tar.gz -C /opt/smartphoto_backend/releases/<release-id>
cp /opt/smartphoto_backend/.env.prod /opt/smartphoto_backend/releases/<release-id>/.env.prod
cd /opt/smartphoto_backend/releases/<release-id>
./scripts/preflight-prod.sh
./scripts/deploy-prod.sh --image-tag <tag> --skip-migrate
```

说明：
- 必须复用同一个 `COMPOSE_PROJECT_NAME`，这样 `postgres/redis/storage` 仍沿用原卷
- 这是默认发布方式，优先于“在旧目录直接覆盖解压”
- 但前提是当前代码线不依赖新的 DB schema；只要代码包里带了新的 Alembic revision，就不能再用 `--skip-migrate`

### 2.3 有迁移发布

适用场景：
- 新增字段、索引、表
- 任何 Alembic revision 变更

```bash
export COMPOSE_PROJECT_NAME=smartphoto_backend
mkdir -p /opt/smartphoto_backend/releases/<release-id>
tar -xzf smartphoto_backend_deploy_<release-id>.tar.gz -C /opt/smartphoto_backend/releases/<release-id>
cp /opt/smartphoto_backend/.env.prod /opt/smartphoto_backend/releases/<release-id>/.env.prod
cd /opt/smartphoto_backend/releases/<release-id>
./scripts/preflight-prod.sh
./scripts/deploy-prod.sh --image-tag <tag>
```

补充说明：
- 若 migration 与旧代码不兼容，禁止直接回滚到旧 tag
- 若迁移执行失败，不要继续 `up -d api worker`
- 若上线后业务接口报 `UndefinedTable/UndefinedColumn/relation does not exist`，优先判断为误用了 `--skip-migrate`

### 2.4 回滚发布

前提：
- 已记录上一个稳定 tag
- 本次 migration 向后兼容，或本次无 migration

```bash
git fetch --tags
git checkout <previous-tag>
docker compose --env-file .env.prod -f docker-compose.prod.yml build api worker
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --force-recreate api worker
docker compose --env-file .env.prod -f docker-compose.prod.yml ps
curl -s http://127.0.0.1:8000/healthz
```

也可直接：
```bash
./scripts/rollback-prod.sh <previous-image-ref>
```

### 2.5 配置变更发布

适用场景：
- `.env.prod` 变更
- `CORS_ALLOW_ORIGINS`、`PUBLIC_BASE_URL`、模型配置、S3 配置调整

仅应用层配置变化：
```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --force-recreate api worker
```

若 `postgres` / `redis` 配置也改了，再重建对应服务：
```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d --force-recreate postgres redis api worker
```

### 2.6 常用运维命令

停止整套服务：
```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml stop
```

启动整套服务：
```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml start
```

彻底停掉容器但保留卷：
```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml down
```

重新拉起：
```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml up -d
```

只重启应用层：
```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml restart api worker
```

查看状态与日志：
```bash
docker compose --env-file .env.prod -f docker-compose.prod.yml ps
docker compose --env-file .env.prod -f docker-compose.prod.yml logs -f api worker
```

### 2.6.1 构建卡在 npm / apt / pip 时的完整替代命令

若 `docker build` 长时间卡在：

- `RUN npm install`
- `RUN apt-get update`
- `RUN pip install --upgrade ...`
- `RUN pip install .`

优先改用下面这套“临时 Dockerfile + 国内镜像源”的完整命令，而不是一直空等：

```bash
set -euo pipefail

export COMPOSE_PROJECT_NAME=smartphoto_backend
export IMAGE_REPO="${SMARTPHOTO_IMAGE_REPO:-smartphoto-backend}"
export IMAGE_TAG=<release-tag>
export IMAGE_REF="${IMAGE_REPO}:${IMAGE_TAG}"

cd /opt/smartphoto_backend/releases/<release-id>

cat > Dockerfile.fast-mirror <<'EOF'
FROM node:20-alpine AS adminfront-builder

ENV NPM_CONFIG_REGISTRY=https://registry.npmmirror.com

WORKDIR /build/adminfront

COPY adminfront/package.json ./
RUN npm install

COPY adminfront/ ./
RUN npm run build


FROM python:3.12-slim AS runtime

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1 \
    PIP_DISABLE_PIP_VERSION_CHECK=1 \
    PIP_DEFAULT_TIMEOUT=120

WORKDIR /app

RUN sed -i 's@http://deb.debian.org@https://mirrors.tuna.tsinghua.edu.cn@g' /etc/apt/sources.list.d/debian.sources \
    && apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

COPY pyproject.toml Readme.md alembic.ini ./
COPY app ./app
COPY alembic ./alembic
COPY scripts ./scripts
COPY --from=adminfront-builder /build/adminfront/dist ./adminfront/dist

RUN PIP_INDEX_URL=https://mirrors.tuna.tsinghua.edu.cn/pypi/web/simple \
    PIP_TRUSTED_HOST=mirrors.tuna.tsinghua.edu.cn \
    pip install --upgrade pip setuptools wheel \
    && PIP_INDEX_URL=https://mirrors.tuna.tsinghua.edu.cn/pypi/web/simple \
       PIP_TRUSTED_HOST=mirrors.tuna.tsinghua.edu.cn \
       pip install . \
    && chmod +x ./scripts/*.sh

EXPOSE 8000

CMD ["./scripts/docker-api.sh"]
EOF

docker build --network host --progress=plain -t "$IMAGE_REF" -f Dockerfile.fast-mirror .
rm -f Dockerfile.fast-mirror
```

### 2.7 发布前检查

```bash
./scripts/preflight-prod.sh
```

重点检查：
- `PUBLIC_BASE_URL` 是否为真实后端外网地址
- `CORS_ALLOW_ORIGINS` 是否包含真实前端 Origin
- `DATABASE_URL` 是否仍指向生产 `postgres`
- `ADMIN_DATABASE_URL` 是否仍为 `sqlite:///./storage/admin.sqlite3`
- `alembic_version` 是否已包含当前代码要求的最新 revision
- `sessions/jobs/idempotency_records` 是否已补齐 `service_id`
- `rule_packs` / `rule_pack_versions` 是否为恢复线期望字段：
  - 应包含 `asset_family/rule_pack_key/config_snapshot/is_published`
  - 不应出现 `family/draft_payload/payload/change_note`
- 若启动报 `ImportError` 且日志中的文件路径指向仓库当前并不存在的模块，优先判断为旧发布目录残留文件污染了 Docker build 上下文
- `LLM_ROUTE_MAIN_PLANNER/LLM_ROUTE_DETAIL_PLANNER` 是否已经切到本次要求的 planner 路由
- `WHATAI_PLANNER_MODEL` 是否已切到 `kimi-k2.5`；若你预期走 WhatAI，不要只改 `OPENROUTER_*` 配置
- `PLANNER_FALLBACK_ROUTE/WHATAI_PLANNER_LIGHT_MODEL/PLANNER_PROFILE` 是否与本次调优方案一致
- `WHATAI_IMAGE_MODEL` 与 `WHATAI_REQUEST_TIMEOUT_SECONDS` 是否保持为用户指定值
- `LLM_PROVIDER` 是否与本次发布方案一致（当前推荐仍为 `whatai`，OpenRouter 只用于文本辅助任务）
- `OPENROUTER_API_BASE/OPENROUTER_API_KEY` 是否已配置
- `LLM_ANALYSIS_MODEL/LLM_PARAMETER_MODEL/LLM_FALLBACK_MODEL` 是否为当前已验证模型
- `IMAGE_SAAS_APP_KEYS/IMAGE_SAAS_DEFAULT_APP_ID` 是否与接入方约定一致
- 若要在 shell 中直接使用 `$POSTGRES_USER/$POSTGRES_DB` 等变量，先执行：

```bash
set -a
source .env.prod
set +a
```

最少执行：

```bash
curl -s http://127.0.0.1:8000/healthz
curl -s http://127.0.0.1:8000/api/admin/v1/auth/health
curl -i -X OPTIONS http://127.0.0.1:8000/api/v2/sessions \

  -H 'Access-Control-Request-Method: POST' \
  -H 'Access-Control-Request-Headers: content-type,x-app-key'
```

后台最小冒烟：
```bash
curl -s -X POST http://127.0.0.1:8000/api/admin/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"admin123456"}'
```

后台增强冒烟：
```bash
curl -s http://127.0.0.1:8000/api/admin/v1/dashboard/overview -H 'Authorization: Bearer <admin_access_token>'
curl -s http://127.0.0.1:8000/api/admin/v1/system/runtime -H 'Authorization: Bearer <admin_access_token>'
curl -s 'http://127.0.0.1:8000/api/admin/v1/sessions?page=1&page_size=5&sort_by=created_at&sort_order=desc' \
  -H 'Authorization: Bearer <admin_access_token>'
```

图片 SaaS 最小冒烟：
```bash
curl -s -X POST http://127.0.0.1:8000/api/v2/sessions \
  -H 'Content-Type: application/json' \
  -H 'X-App-Key: <app-key>'
curl -s http://127.0.0.1:8000/api/v2/sessions/<session_id> \
  -H 'X-App-Key: <app-key>'
```

预期：
- 图片主链路能成功调用：
  - `POST /api/v2/sessions/<session_id>/detail-pages/strategy/preview`
  - `POST /api/v2/sessions/<session_id>/detail-pages/generations`
  - `GET /api/v2/sessions/<session_id>/detail-pages/results`
- 同一 `session_id` 下还能继续调用：
  - `POST /api/v2/sessions/<session_id>/results/global-edit`
  - `POST /api/v2/sessions/<session_id>/results/regenerate`
  - `POST /api/v2/assets/<asset_id>/regenerate`
- 下载类接口在带正确 `X-App-Key` 时可正常返回 ZIP/图片
- `GET /api/admin/v1/dashboard/overview` 能返回 `runtime_cards/ops_cards/config_cards`
- `GET /api/admin/v1/system/runtime` 能返回 `queue_stats`
- `GET /api/admin/v1/sessions` 响应中应包含统一分页字段 `page/page_size/total/total_pages`

如果本次涉及上传链路，再补：
1. `POST /api/v2/uploads/presign`
2. 直传对象存储
3. `POST /api/v2/uploads/complete`
4. 若前端部署在 ESA / CDN Worker / 边缘代理后，不要继续把移动端或生产 Web 的图片二进制经 `POST /api/v2/sessions/{id}/images` 直传到 API；优先走 `presign -> PUT -> complete`，避免边缘层对 multipart 长连接返回 `524`
5. 若线上仍出现上传 `524/504`，先在浏览器 Network 里确认真正发出去的上传请求：
   - 若是 `POST /api/v2/sessions/{id}/images` 这类 multipart，请优先怀疑前端仍是旧包或调用了旧接口
   - 若是 `/api/v2/uploads/direct/<upload_id>` 相对路径，请优先怀疑生产 `STORAGE_BACKEND=local`，所谓“直传”实际上仍经过 API
   - 若是对象存储域名的预签名 URL，再重点排查对象存储、边缘网络或前端文件大小
6. 当前实现已增加两层兜底：
   - 前端在 `presign` 前先拦截超过 `10MB` 的文件，直接提示 `40007 file_too_large`
   - 后端本地 `PUT /api/v2/uploads/direct/{upload_id}` 改为流式写盘，不再 `await request.body()` 一次性吃完整文件

如果本次涉及异步任务，再补：
1. 触发一条最小 job
2. 查看 worker 日志
3. 检查 `/jobs/{job_id}` 或 SSE 事件流

### 2.10 问题：部分大图上传返回 `524/504`

先判断到底是前端问题还是后端问题：

```bash
# 1) 打开浏览器开发者工具 Network，重新上传失败图片，观察真正超时的请求 URL
# 2) 同时在服务器看 API 日志
cd /opt/smartphoto_backend
docker compose --env-file .env.prod -f docker-compose.prod.yml logs --tail=200 -f api
```

判定标准：
- 如果超时请求是 `POST /api/v2/sessions/<session_id>/images`：
  - 这是旧版 multipart 直传路径，问题优先在前端接入或前端发布物未更新
- 如果超时请求是 `/api/v2/uploads/direct/<upload_id>`：
  - 这是 local storage 的“伪直传”，二进制仍经过 API；问题优先在后端部署形态
- 如果超时请求是对象存储签名 URL：
  - 前后端上传链路基本正确，优先排查对象存储连通性、边缘网络、文件体积和客户端网络

服务器侧快速核对：

```bash
cd /opt/smartphoto_backend
set -a
source .env.prod
set +a

echo "== storage backend =="
grep '^STORAGE_BACKEND=' .env.prod

echo "== cors origins =="
grep '^CORS_ALLOW_ORIGINS=' .env.prod

echo "== runtime view =="
curl -s http://127.0.0.1:8000/api/admin/v1/system/runtime | python3 -m json.tool | sed -n '1,120p'
```

重点看：
- `STORAGE_BACKEND=s3` 才是真正推荐的生产上传方式
- 如果线上还是 `local`，前端即使走了 `presign`，上传体也仍会打到 API

当前代码修复点：
- 前端在发起 `POST /api/v2/uploads/presign` 前就拦截 `>10MB` 文件，避免用户等待到边缘超时
- 本地 `PUT /api/v2/uploads/direct/{upload_id}` 已改成流式写盘，降低 API 内存占用和长请求风险

如果线上需要进一步确认对象存储直传是否生效，可抓一次 presign 返回：

```bash
curl -s -X POST http://127.0.0.1:8000/api/v2/uploads/presign \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <access_token>' \
  -d '{
    "session_id": "<session_id>",
    "upload_kind": "session_image",
    "original_name": "debug.jpg",
    "content_type": "image/jpeg",
    "size_bytes": 123456,
    "display_order": 1,
    "slot_type": "front"
  }' | python3 -m json.tool
```

重点看 `data.upload_url`：
- 若是业务 API 域名下的 `/api/v2/uploads/direct/...`，说明当前不是对象存储直传
- 若是 OSS / S3 预签名 URL，说明上传体不会经过 API

## 3. 任务链路排障

### 3.1 问题：任务长期停在 queued
排查路径：
1. Worker 是否运行
2. Worker 是否监听正确队列（`q.analysis,q.copy,q.generation.main,q.generation.detail`）
3. Redis 是否可连通
4. Job 是否已创建但未分发

建议检查：
```bash
# 观察 worker 日志（如果通过终端直接启动，直接看终端输出）
# 如通过 docker/pm2 部署，请查看对应日志
```

SQL 辅助：
```sql
SELECT id, job_type, status, queued_at, started_at
FROM jobs
ORDER BY created_at DESC
LIMIT 20;
```

### 3.2 问题：任务停在 running
排查路径：
1. 看 `/jobs/{id}` 中 `stage/error_code/error_message`
2. 看 `/jobs/{id}/events` 是否仍有增量事件
3. 检查上游接口可用性（50201/50202）
4. 检查存储路径可写权限（`STORAGE_ROOT`）
5. 如需核对 prompt 和参考图引用，单独调用 `/sessions/{id}/prompts/preview`
6. 若本轮走详情页独立生成，改查 `/sessions/{id}/detail-pages/prompts/preview`

建议检查：
```bash
curl -s http://127.0.0.1:8000/api/v2/jobs/<job_id>
curl -N http://127.0.0.1:8000/api/v2/jobs/<job_id>/events
curl -s -X POST http://127.0.0.1:8000/api/v2/sessions/<session_id>/prompts/preview \
  -H 'Content-Type: application/json' \
  -d '{"instruction":"主体更靠中间","include_latest_assets":true}'
curl -s -X POST http://127.0.0.1:8000/api/v2/sessions/<session_id>/detail-pages/prompts/preview \
  -H 'Content-Type: application/json' \
  -d '{"instruction":"标题更清晰","include_latest_assets":true}'
```

Step 5 策略排查：
```bash
curl -s -X POST http://127.0.0.1:8000/api/v2/sessions/<session_id>/strategy/preview \
  -H 'Content-Type: application/json' \
  -d '{"planner_instruction":"白底图更标准，主图更像参考图","slot_preferences":[{"slot_id":"proof_authority","expression_mode":"certificate_proof","locked":true}]}'
```

补充说明：
- `POST /api/v2/sessions/{id}/strategy/preview` 当前仍是同步接口；若前端部署在 ESA / CDN Worker / 边缘函数后面，且该层超时只有 15~30 秒，可能先收到 `504`，而不是后端业务错误
- 若同一份 session 输入重复触发策略预览，后端会优先复用已缓存的 `strategy_preview`；前端遇到超时后应等待几秒再重试，不要立刻继续调用 `/generations`
- 若 worker 日志出现 `cannot transition created -> analyzing`，说明某些 session 在触发分析时状态仍为 `created`；当前实现已在 API 入口和 worker 两侧兼容补正为 `images_uploaded -> analyzing`
- 若下载或结果接口返回 `40101 unauthorized`，优先检查：
  1. 请求头是否带了正确的 `X-App-Key`
  2. 当前 `session_id/job_id` 是否属于该 `service_id`
  3. `.env.prod` 中的 `IMAGE_SAAS_APP_KEYS` 是否与接入方约定一致
- 若 API 启动后图片主链路全部 401，优先检查 `IMAGE_SAAS_APP_KEYS` 格式是否正确，例如 `["default:prod-app-key"]`
- 若 `OPTIONS /api/v2/sessions` 返回 `Disallowed CORS origin`，说明 `.env.prod` 的 `CORS_ALLOW_ORIGINS` 未包含真实前端域名；修复后必须 `up -d --force-recreate api worker`
- 若执行 `psql -U "$POSTGRES_USER"` 一类命令时报 `unbound variable`，先执行 `set -a && source .env.prod && set +a`
- 若临时构建命令报 `FileNotFoundError: Dockerfile`，先确认已 `cd` 到当前 release 目录，不要在 SSH 断线重连后默认留在 `/root`

### 3.3 问题：409 并发冲突（job_already_running）
含义：同 session 已有运行中的生图任务。

排查路径：
1. 查询该 session 是否存在 `queued/running` 的生成类任务
2. 如果 Redis 可用，检查锁键是否残留

SQL 辅助：
```sql
SELECT id, session_id, user_id, job_type, status
FROM jobs
WHERE job_type IN ('generate_gallery','regenerate_gallery','global_edit','regenerate_asset','generate_detail_page')
  AND status IN ('queued','running')
ORDER BY created_at DESC;
```

Redis 辅助：
```bash
redis-cli KEYS 'lock:*:generation'
```

### 3.4 问题：上游失败（50201 / 50202）
排查路径：
1. `.env` 中 `WHATAI_API_KEY`、`OPENROUTER_API_KEY` 是否按链路分别配置
2. `WHATAI_API_BASE`、`OPENROUTER_API_BASE`、模型名是否正确
3. 网络出口是否可访问上游
4. 上游返回结构是否变更

补充说明：
- 现在要区分两条上游链路：
  - 视觉主链（analysis / 主图 planner / 详情页 planner / 首轮参数提取）：默认 `WhatAI + Gemini`
  - 文本辅助任务（Step 3 completion / 主图文字设计 / 详情页文字 reviewer）：默认 `OpenRouter`
  - 图片生成：`WHATAI_*`
- 不要把 OpenRouter 当成视觉主链全局替代者；若稳定链路突然漂移，优先检查是否误改了按任务路由
- 若上游返回 `400 Bad Request`，优先检查当前模型对应的请求协议是否正确
- `gemini-*` 文本模型当前通过 Gemini 官方 `generateContent` 协议请求
- Step 2 分析与 Step 5 planner 当前都会把 session 图片以内联图像内容发给上游，不再依赖本地 URL 可被公网访问
- Step 2 分析当前会优先用缩边后的参考图，降低大图直传导致的超时和内存峰值
- Step 2 的 `supplement_image_recommendations` 现在是“建议补传什么图”，如果前端还显示成抽象拍摄建议，优先检查前端是否仍在消费旧字段映射
- 主图组默认优先走 `/v1/images/edits`，把参考图 multipart 上传给上游；若上游返回 `task_id`，再轮询任务结果
- 生图链路当前改为“批量提交全部任务 -> 集中轮询全部 task_id -> 并发下载结果”
- 默认轮询策略由 `IMAGE_POLL_PROFILE` 控制，缺省为 `5s x 6 + 10s x 12 + 15s x 20`，总窗口约 7.5 分钟；`NOT_START` 不视为失败
- 主图和详情页默认分发到独立队列：`q.generation.main` / `q.generation.detail`
- 日志会附带上游响应正文，便于直接定位模型参数或协议不兼容
- 若 WhatAI 报 `aspect_ratio must be one of ...`，优先检查当前是否把像素尺寸（如 `1792x768`）误传给了 `/images/edits`；当前实现要求 edit 请求传 `aspect_ratio`，而不是 `size`
- 若上游报 `Server disconnected without sending a response.`，优先检查该次 WhatAI 任务是否已在中转后台生成成功；当前实现会尽量通过任务结果轮询与图片下载重试拿回链接，避免重复提交生图请求
- `/images/edits` 若在提交阶段发生传输层断连，当前实现会先做请求级重试；若仍失败，只对当前单张图做内部重试，不会整组重跑
- 若要排查“为什么这张图是这样生成的”，优先看 `POST /sessions/{id}/prompts/preview` 的 `prompts`、`reference_manifest` 和 `latest_assets.generation_snapshot`
- 若当前走详情页链路，优先看 `POST /sessions/{id}/detail-pages/prompts/preview` 的 `detail_story_brief`、`prompts`、`product_reference_manifest`、`style_reference_manifest` 和 `latest_assets.generation_snapshot`
- 若怀疑详情页所有 panel 看起来像一张图，优先检查 `detail_strategy_preview.panel_plan[*].product_reference_ids/style_reference_ids` 与 `generation_snapshot.effective_reference_image_ids`
- 若怀疑详情页局部图和真实商品结构对不上，优先检查：
  - `detail_strategy_preview.panel_plan[*].visual_truth_mode`
  - `detail_strategy_preview.panel_plan[*].origin_note`
  - `assets.generation_snapshot.global_consistency_note`
  当前实现会用这些字段区分“真实局部放大”和“机制示意图”
- 若白底图失败，优先检查 `latest_assets.generation_snapshot.white_bg_validation` 或 worker 日志中的白底校验指标；当前是否触发白底校验取决于 `requires_white_bg_validation` 能力标记，而不是固定 role 名称

说明：当前实现在无 key 时会使用占位输出，便于本地链路调试。

### 3.4.1 问题：`UndefinedColumn: column assets.generation_snapshot does not exist`
含义：代码已经升级到依赖 `assets.generation_snapshot` 的版本，但数据库仍停在旧迁移。

排查路径：
1. 执行 `./.venv/bin/alembic current`
2. 确认当前 revision 是否落后于 `./.venv/bin/alembic heads`
3. 执行 `./.venv/bin/alembic upgrade head`
4. 再次访问 `GET /sessions/{id}/results`

补充说明：
- 当前 `./scripts/dev-api.sh` 与 `./scripts/dev-worker.sh` 启动前会自动补一次迁移
- 若 API/Worker 已经在旧 schema 上运行，补完迁移后通常无需重建数据库，只需继续使用或重启进程

### 3.4.2 问题：详情页接口报缺列或缺表（如 `sessions.detail_strategy_preview` / `detail_style_images` / `assets.asset_family`）
含义：代码已经升级到包含详情页独立生成版本，但数据库仍停在旧迁移。

排查路径：
1. 执行 `./.venv/bin/alembic current`
2. 确认当前 revision 是否落后于 `./.venv/bin/alembic heads`
3. 执行 `./.venv/bin/alembic upgrade head`
4. 再次访问 `POST /sessions/{id}/detail-pages/strategy/preview`

### 3.4.3 问题：Step 2 / 后台品类管理报缺表（如 `relation "category_catalogs" does not exist`）
含义：代码已经升级到“全局品类库 + Prompt-first analysis”版本，但数据库还没执行新增表迁移。

排查路径：
1. 执行 `./.venv/bin/alembic current`
2. 确认当前 revision 是否落后于 `./.venv/bin/alembic heads`
3. 执行 `./.venv/bin/alembic upgrade head`
4. 再次访问 `POST /sessions/{id}/analysis` 或后台 `/api/admin/v1/category-catalog`

补充说明：
- Step 2 analysis 现在优先消费后台启用的全局品类库；如果这张表不存在，analysis 和后台品类管理都会报错
- 新增客户品类时，优先走后台 `Category Catalog` 配置，不要回到 `upstream.py` fallback 里加硬编码

### 3.4.4 问题：Step 3 页面内容为空，或看起来像没有真正生成
排查路径：
1. 先查前端是否至少调用过：
   - `POST /api/v2/sessions/{session_id}/parameters/extract`
2. 当前默认主链不再要求 `POST /parameters/complete`。
3. 再查 `GET /api/v2/sessions/{session_id}/parameters` 是否返回：
   - `parameter_snapshot`
   - `source_mode`
   - `evidence_priority`
   - `relevance_status`
   - `rejection_reason`
4. 若 `relevance_status=invalid`，优先确认附件是否与当前商品直接相关；没有附件时，检查 Step2 analysis 和商品图是否已准备好。

补充说明：
- Step 3 默认已经收口为单次 `extract` 结果，不再依赖二次补全接口
- `parameters/complete` 仍是兼容接口，但不应被前端当成主链必经步骤

### 3.4.5 问题：后台 / Worker 看不到详情页链路阶段
排查路径：
1. 查询详情页 job 是否为：
   - `generate_detail_page`
   - `regenerate_detail_panel`
2. 再查 `job_events` 是否包含详情页专属阶段：
   - `detail_strategy_ready`
   - `detail_panel_render_started`
   - `detail_panel_render_succeeded`
   - `detail_stitched_ready`
3. 查看后台 Overview / Runtime 卡片里是否已有：
   - `detail_running_jobs`
   - `detail_failed_rate_24h`
   - `detail_avg_duration_24h`

SQL 辅助：
```sql
SELECT job_id, event_type, message, created_at
FROM job_events
WHERE job_id = '<detail_job_id>'
ORDER BY created_at ASC;
```

### 3.5 问题：下载 ZIP 为空或版本不符
排查路径：
1. 先查 `GET /sessions/{id}/results` 看 `latest_result_version`
2. 下载接口是否指定了错误 `version`
3. 对应版本 `assets` 是否为 `ready`
4. 存储文件是否存在于 `STORAGE_ROOT`

SQL 辅助：
```sql
SELECT id, version_no, status, image_url
FROM assets
WHERE session_id = '<session_id>'
ORDER BY version_no DESC, display_order ASC;
```

### 3.6 问题：单图重生成后旧版本看不到
排查路径：
1. 先查 `GET /sessions/{id}/results` 的 `available_versions`
2. 再查 `GET /sessions/{id}/results?version=<旧版本>` 是否还有旧版本快照
3. 若是旧数据在历史实现中被错误标成 `superseded`，执行修复脚本

修复命令：
```bash
./.venv/bin/python scripts/repair_version_history.py
```

补充说明：
- 当前实现已改成“历史版本保留 + 单图重生成物化完整新版本”
- 修复脚本会恢复旧版本可见性，并补齐缺失的 carry-forward 资产

## 5. 联调脚本化检查清单
以下流程用于验证最短可用链路：
1. 创建会话
2. 上传图片
3. 触发分析
4. 选择平台
5. 保存 copy
6. 生成策略预览
7. 触发生图
8. 查询 job 与 SSE
9. 查询结果
10. 查看 prompt preview（可选）
11. 下载 ZIP

示例（按需替换变量）：
```bash
BASE=http://127.0.0.1:8000/api/v2
SID=$(curl -s -X POST "$BASE/sessions" | jq -r '.data.session_id')

curl -s -X POST "$BASE/sessions/$SID/images" \
  -F "file=@./demo.jpg;type=image/jpeg" \
  -F "slot_type=front" \
  -F "display_order=1"

curl -s "$BASE/sessions/$SID"
curl -s -X POST "$BASE/sessions/$SID/analysis"
curl -s -X PUT "$BASE/sessions/$SID/platform-selection" \
  -H 'Content-Type: application/json' \
  -d '{"selected_platform_ids":["temu"],"active_platform_id":"temu"}'

curl -s -X PUT "$BASE/sessions/$SID/copy" \
  -H 'Content-Type: application/json' \
  -d '{"product_name":"测试产品","category":"测试类目","headline":"测试标题","selling_points":"卖点A","usage_scenes":"客厅","specs":"参数A","style_choice":"现代简约","style_custom":"","key_parameters":[]}'

curl -s -X POST "$BASE/sessions/$SID/strategy/preview"
curl -s -X POST "$BASE/sessions/$SID/strategy/preview" \
  -H 'Content-Type: application/json' \
  -d '{"planner_instruction":"白底图更标准，主图更像参考图","slot_preferences":[{"slot_id":"proof_authority","expression_mode":"certificate_proof","locked":true}]}'
JOB_ID=$(curl -s -X POST "$BASE/sessions/$SID/generations" \
  -H 'Content-Type: application/json' -d '{"instruction":null}' | jq -r '.data.job_id')

# 只调试单个主图槽位
SINGLE_JOB_ID=$(curl -s -X POST "$BASE/sessions/$SID/generations" \
  -H 'Content-Type: application/json' \
  -d '{"instruction":"先试一张","slot_ids":["proof_authority"]}' | jq -r '.data.job_id')

curl -s "$BASE/jobs/$JOB_ID"
curl -s "$BASE/sessions/$SID/results"
curl -s -X POST "$BASE/sessions/$SID/prompts/preview" \
  -H 'Content-Type: application/json' \
  -d '{"instruction":"主体更靠中间","include_latest_assets":true}'

# 详情页独立生成链路（可替代主图生成）
curl -s -X POST "$BASE/sessions/$SID/detail-pages/style-images" \
  -F "file=@./style.jpg;type=image/jpeg" \
  -F "display_order=1"
curl -s -X POST "$BASE/sessions/$SID/detail-pages/strategy/preview" \
  -H 'Content-Type: application/json' \
  -d '{"planner_instruction":"标题更短，版式更清晰","panel_preferences":[{"slot_id":"detail_slot_02","panel_type":"parameter_explainer","display_order":2,"locked":true}]}'
DETAIL_JOB_ID=$(curl -s -X POST "$BASE/sessions/$SID/detail-pages/generations" \
  -H 'Content-Type: application/json' -d '{"instruction":"整体更高级"}' | jq -r '.data.job_id')
curl -s "$BASE/jobs/$DETAIL_JOB_ID"
curl -s "$BASE/sessions/$SID/detail-pages/results"
```
